Produto: Pipeline SDD · Laboratório: RidersBNU

O pipeline é o produto.
RidersBNU é o laboratório.

RidersBNU — app de organização de encontros de motociclistas em Blumenau — não é o ponto desta apresentação, é a prova de campo. O que está sendo medido aqui é um pipeline de agentes especializados em Spec-Driven Development (SDD), e RidersBNU é o laboratório onde ele rodou de verdade: 17 dias corridos, do PRD ao deploy em produção, sem equipe de desenvolvimento — só o pipeline, se testando nele mesmo em cada feature.

O produto

Nenhuma etapa pula a anterior

O pipeline SDD (btt-sdd) orquestra um agente especializado por etapa. Toda feature nasce de um PRD, passa por desenho técnico revisável e só chega a produção depois de revisão de código, QA, segurança e SRE — cada etapa com seu próprio agente e seu próprio artefato escrito. RidersBNU é onde essa sequência rodou 20 vezes seguidas, sem exceção.

Quando uma feature é grande, o TRD a divide em fatias verticais de entrega — cada fatia é sua própria branch, seu próprio PR e passa pelas etapas 03–07 inteiras antes da próxima começar. É por isso que 20 features viraram 153 PRs: features como 0008-categorias-de-eventos e 0011-ocultar-usuarios-de-teste tiveram 5 fatias cada, todas em produção antes da seguinte iniciar.

Cachorro comendo a própria ração

O pipeline se testa nele mesmo

Dogfooding: quem constrói a ferramenta é o primeiro a viver com ela. Enquanto RidersBNU era construído, o pipeline que o construía também estava sendo desenvolvido — e cada fricção real encontrada no laboratório virou ajuste no produto, sincronizado de volta para dentro do mesmo projeto que a encontrou.

Prova de que o loop fecha, não só de que ele existe

O próprio pipeline não tinha uma seção formal para "lições aprendidas recorrentes"

Durante a revisão de SRE da primeira fatia de specs/0004-deploy-backend-heroku, o agente precisou registrar um padrão de falha recorrente — mas docs/QUALITY-GATES.md (o próprio guia de governança do pipeline) ainda não tinha essa seção formalizada. Em vez de ignorar, o agente criou o mecanismo ali mesmo, no laboratório (docs/LESSONS-LEARNED.md), e deixou registrada a recomendação explícita: formalizar essa seção é responsabilidade de quem mantém o pipeline, não do projeto que o usa.

É esse arquivo — nascido de uma lacuna real, encontrada usando o produto de verdade — que hoje rastreia as 10 lições aprendidas citadas nesta apresentação.

O que o gate pegou

Bugs que não chegaram ao usuário

O pipeline registra formalmente todo padrão de falha que se repete em duas ou mais features (docs/LESSONS-LEARNED.md) — para a revisão seguinte citar o padrão em vez de redescobri-lo. Quatro exemplos reais, com o que teria acontecido sem a etapa que pegou.

Undelete silencioso de evento excluído

LL-7 · bloqueante

Um campo novo (deletedAt) não era propagado por três casos de uso que reconstroem o agregado Volta. Resultado: editar um evento excluído restaurava ele silenciosamente, sem passar pela guarda de autorização de exclusão.

Pego por: revisão de segurança (SEC-0012-1), bloqueou o merge até a correção no mesmo PR.

Bypass de autorização sob impersonação de tenant

LL-9 · 3 ocorrências

Um guard resolvia a identidade de quem fazia a requisição pelo tenant atual do contexto — que durante uma impersonação de administrador é o tenant do alvo, não o do administrador. Reapareceu em 3 features diferentes.

Pego por: code review, todas as 3 vezes — na 3ª ocorrência, a regra de "nunca repetir uma pergunta mais de 3 vezes" acionou uma pergunta formal ao usuário em vez de mais uma linha de registro passivo.

Bug de build invisível a lint, typecheck e testes unitários

LL-3

Uma função passada como prop atravessando a fronteira Server→Client Component do Next.js só quebrava em next build — nunca em jest/tsc/lint. Passou por 2 rodadas de code review e 2 de QA sem ser detectado.

Pego por: SRE, após 10 execuções de CI em falha — motivou incluir npm run build na verificação padrão de toda mudança de composição de tela, antes do SRE, não depois.

Conta duplicada por e-mail sensível a maiúsculas

LL-5

Login por senha e login via Google, com capitalizações diferentes do mesmo e-mail, criavam duas contas em vez de uma — e a correção inicial abriu um vetor de account takeover (vincular identidade sem exigir e-mail verificado pelo provedor).

Pego por: investigação de bug de produção → corrigido → o próprio fix revisado encontrou o problema mais grave (CR13-1) antes de ir ao ar.

Honestidade, não destaque

O que ainda está em aberto

Um relatório de telemetria que só mostra vitória não serve para nada. Isto segue pendente, documentado e rastreado — não escondido.

Environment "production" do GitHub sem aprovação manual obrigatória

LL-2 · 18 ocorrências

Reconfirmado em 18 rodadas de revisão de SRE ao longo de 10 features distintas — desde que os dois gates de deploy automático foram ligados, cada merge em main dispara deploy real em produção sem um gate de aprovação humana dedicado no ambiente.

Status: é configuração de painel do repositório, fora do mandato de qualquer agente do pipeline resolver sozinho — na 18ª ocorrência, o SRE finalmente formalizou a pergunta ao usuário em vez de só reconfirmar passivamente mais uma vez.

Duas moedas de propósito, não por descuido: a infraestrutura é faturada em dólar (Heroku, Cloudflare, GitHub) e a assinatura do Claude Code em real — conversão não incluída para não embutir uma cotação que muda a cada dia. O plano do GitHub (US$ 49/ano) foi amortizado em ~US$ 4/mês; os US$ 5 de estouro de CI são deste ciclo específico — 153 PRs rodando a suíte completa de testes a cada push consome minuto de Actions rápido, é o preço direto de nunca pular a verificação automatizada antes do merge. Somando os dois blocos: uma pessoa, ~US$ 20/mês de produção real + R$ 500/mês de ferramenta, entregou 20 features completas em 17 dias. Fora desta conta: o domínio próprio, já existente antes deste projeto começar. Nenhum custo de equipe, agência ou freelancer entrou aqui — o pipeline substituiu esse orçamento, não o comparou com ele.
